> **The observer that observes itself observes nothing else**

## Session Overview

Continued Effect-Atom testbed work. Prime wanted render tracking badges on all hypotheses — a noble pursuit of observability. The irony? Building the observer became the observed bug.

## Incident: H3.4a — useAtom + useEffect Infinite Loop

**Symptom:** `Maximum update depth exceeded`

**Root Cause:**
```
useAtom(trackingAtom)  →  SUBSCRIBES to atom
      ↓
useEffect updates atom  →  triggers subscription
      ↓
component re-renders  →  useEffect runs again  →  ∞
```

Tried to apply the H5 lesson (Atom.family for isolation) to the meta-tracking system itself. Poetic. Wrong.

**The Trap:** `useAtom` returns `[value, setter]` — that `value` creates a subscription. Even if you destructure `[, setter]` and ignore the value, the hook still subscribes. When useEffect fires on every render and calls that setter, the subscription triggers a re-render. Loop complete.

**Fix:** Module-level Map. No React state for the actual tracking — just synchronous mutations to a plain JS object. Display uses isolated `useState` + `setInterval` polling. The observer becomes invisible to React's reconciliation.

## Architecture Decision

**Before:** Atom.family with shared subscriptions
**After:** Module-level storage with polling display

The tracking system now has three layers:
1. `renderTrackingStore` — Map<HypothesisKey, State> (module-level, no React)
2. `useTrackRender(key)` — synchronous increment during render phase
3. `useRenderStats(key)` — isolated polling for badge display

Each badge polls independently. No cascades. No loops.
